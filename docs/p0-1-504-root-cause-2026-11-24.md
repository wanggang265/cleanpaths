## 0. 结论一句话

504 不是源站进程问题：站点是 100% 静态站（Next.js export → Cloudflare Pages，无传统源站），根因是 `functions/_middleware.js`（pages.dev noindex 中间件）把**每一个 HTML 页面请求都包进 Pages Functions（Workers）runtime**，叠加 O2O 双跳（cleanpaths.io → cleanpaths.pages.dev），而 11-17~11-24 窗口内 Cloudflare 自身爆发多起 Workers/PoP/网络 5xx 事件，Workers 停滞时 CF 边缘等待内跳响应超过 100s 上限即报 504；HTML 无边缘缓存（100% 回源），故障按流量分布，故"集中"在请求量最大的 5 个页面。真实用户影响面≈0（GA4 90 天仅 67 用户），主要受害面是 Googlebot 爬取（SEO）。

## 3. 真实用户 vs 扫描器分流

- 请求量口径：CF 7 天 18081 请求 ≈ 2583/天；HTML 类（dynamic 61.3%）≈ 11084/7d ≈ 1583/天。
- 真实用户口径：GA4（8/26-11-23）67 用户、organic 7 会话 ≈ **1-2 个真实用户/天**。
- 结论：**HTML 请求 ≥97% 来自爬虫/扫描器/AI 采集器**（方法：请求量与 GA4 用户量比值；UA 级精确分流需 zone.analytics/logpush 权限，当前两个 token 均无 analytics.read——与 P1-1「Rulesets 读权限缺失」同一 known-gap，标 [待确认]）。
- 504 用户受影响面：725 次 × 真实用户占比(<1-2%) ≈ **<15 次/7 天，大概率≈0**；扫描器打出的 504 不构成用户受影响面。**真正受损的是 Googlebot**：GSC 已收录 28 页且带 3 严重问题（404、已抓取未收录、robots）与 504 时段重合，爬取预算被 504 侵蚀——这是 P0-6 的输入。

## 4. 根因因果链（可复述版）

哪个进程：无源站进程；故障面 = Pages Functions（Workers）runtime + O2O 内跳（cleanpaths.io → cleanpaths.pages.dev）。
哪类请求：全部未命中边缘缓存的请求，首当其冲是 HTML 页面请求（max-age=0 → DYNAMIC → 100% 回源且 100% 过 Workers middleware）。
为什么超时：CF Workers/PoP 事件窗口内 invocation 停滞，O2O 内跳无响应，CF 边缘等待超 100s 上限 → 504；间歇期全站 TTFB 40~85ms。请求分布决定 504 计数集中 Top 页（/、/pt/png-para-dxf/、/png-to-dxf/、/pricing/、/refund/）——是均匀故障×流量占比，不是这 5 个路径本身有问题。

排除项：部署传播（4 次/success，覆盖不了 725 次持续分布）；源站资源（无源站）；API 函数 hang（license/verify、checkout、beacon 实测 75~420ms 返回；feedback 的 Telegram await 无超时保护是真实瑕疵但流量≈0，不构成 725 次，已另记 P2 建议）；扫描器专打某路径（504 按流量分布而非路径特征分布）。

## 5. 修复（已部署，禁"重启式"）

**变更：新增 `public/_routes.json`（构建落 out/ 根），include 仅 ["/api/*", "/admin/*"]。**

- 效果：Pages 路由改为「仅 API/admin 调用 Functions，静态页/资产 100% 走资产层直出」→ HTML 请求彻底脱离 Workers runtime（与 A3 同一快路径，实证稳定）。
- 部署：build 过 gate → `wrangler pages deploy out` → 部署 **87ee47f1-02f5-44d7-b874-754091f940a2**（2026-11-24T13:18:14Z）成为 canonical。
- 部署后验证（13:1x~13:2x UTC）：
  1. pages.dev HTML **x-robots-tag 消失** = middleware 不再被 HTML 请求调用（架构级直接证明）✅
  2. POST /api/license/verify 仍 200 `{"ok":true,"valid":false}`（Functions 在 /api/* 正常路由）✅
  3. cleanpaths.io/ 200、37ms TTFB、canonical 在位 ✅
- 回滚：删除 public/_routes.json 重新部署即可（一行还原）。
- 顺带收益：HTML 响应不再被 Function 包裹压头（未来做 P1-1 缓存规则时不再有 Function 层干扰）。

**已接受的策略级副作用（需齿轮/zhongshu 知晓）**：pages.dev 的静态 HTML 不再带 `X-Robots-Tag: noindex`（middleware 只剩 /api/*、/admin/* 覆盖，对 SEO 无意义）。防重复收录保护改由：47/47 页 canonical 指向 cleanpaths.io（实测全量，含 PT 页）+ sitemap 仅含 cleanpaths.io + pages.dev 无外链。残余风险=极低；如需双保险，可另行决策关闭项目 Preview Deployments（独立设置变更，不在本工单擅动）。

## 7. 遗留建议（不阻塞本工单）

- P2：functions/api/feedback.ts `sendTo()` 对 Telegram fetch 无超时保护（compare webhooks/creem.ts 已有 5s race）——低流量不构成 504 主因，但建议补 Promise.race 上限。
- P1-1 联动：HTML 边缘缓存规则（短 TTL）可把 O2O 内跳也隔离出请求路径，是 504 类故障的最终绝缘层；按计划在 P0 验收后执行。
- 观测：若未来再现 504 且当时无 CF 事件，再查 O2O 层；本次证据不支持任何"站点代码/进程"侧根因。
